How to Architect a Hybrid, Container-Based Solution on AWS

  • ❓ When half your workloads stay on-premises and half move to AWS, how do you connect the two, keep containers portable, migrate a database with near-zero downtime, and stay resilient — without rewriting applications?
  • Hint: same discipline as 10. Serverless Backend and 11. Serverless Data Analytics — requirements → architectural drivers → candidate services → trade-offs → decision → justified rejections. What changes is that the answer now spans two environments joined by a network.

Running example used throughout this chapter

An enterprise runs containerised applications and PostgreSQL databases in its own data centres. Data-centre contracts are expiring in waves, so it will move half the workloads to AWS now and keep the rest on-premises until their contracts end — a genuinely hybrid end state, not a big-bang migration.

The customer’s constraints:

  • Dedicated, consistent, low-latency connectivity between the data centre and AWS for high-volume traffic.
  • Keep containers private (no inbound internet) but allow outbound (e.g. to pull updates).
  • Same orchestration tooling on both sides to simplify operations.
  • Lift-and-shift PostgreSQL to AWS with no application code rewrite.
  • High uptime, resilience, fault tolerance — no single points of failure.
  • On-prem apps must store/read data in AWS over NFS without refactoring.

12.1 The Method: nine steps across two environments

A hybrid design decomposes into the same reasoning chain as a cloud-only one — but every answer must hold in both environments, and the network underneath them.

Architect’s takeaway: In hybrid design, the network is the foundation — get connectivity wrong and every other decision inherits its latency, cost and failure modes.

12.2 Step 1 — Turn requirements into drivers

  • ❓ How does “half here, half there, for years” change the design?

Customer requirement Architectural driver Implication
Half on-prem for years Hybrid, not migration Invest in durable connectivity and shared tooling
High-volume, consistent traffic Dedicated connectivity Direct Connect, not internet VPN as the primary
Private containers, outbound only Controlled egress Private subnets + NAT / VPC endpoints
Same tooling both sides Operational consistency ECS Anywhere + Systems Manager agents on-prem
No application rewrite Compatibility over optimality Managed engine that speaks the same wire protocol
No single points of failure Redundancy at every layer Multi-AZ, multi-link, multi-NAT
Keep NFS Protocol preservation Hybrid file gateway, not a client refactor

⚠️ Plan the address space before anything else. The most common hybrid blocker is overlapping CIDR ranges between the data centre and the VPC — routing simply cannot resolve it, and the fix (re-IP or NAT the overlap) is painful once workloads are live. Agree non-overlapping ranges at design time.

Architect’s takeaway: “Half and half, for a long time” is the driver that shapes everything: it rules out a big-bang migration and forces you to invest in durable connectivity and consistent tooling rather than treating on-prem as throwaway.

12.3 Step 2 — Connect the two environments

  • ❓ Dedicated line, encrypted tunnel, or a central hub — and when does each win?

12.3.1 The connectivity decision

Chosen: AWS Direct Connect. The customer needs consistent, dedicated throughput for high-volume DC↔︎AWS traffic. Direct Connect keeps traffic on the AWS global network, never on the public internet, which removes the latency spikes and bottlenecks you’d get over the internet.

🔴 Private is not the same as encrypted. Direct Connect traffic is not encrypted by default — it is a private circuit, not a secure one. If your compliance posture requires encryption in transit across the link, you must add it: MACsec (on supported dedicated connections) for layer-2 encryption, or run an IPsec Site-to-Site VPN over the Direct Connect public virtual interface. Do not let “off the public internet” be read as “encrypted”.

⏱️ Direct Connect has a lead time — and here it is on the critical path. A dedicated connection requires a cross-connect at a Direct Connect location (LOA-CFA, partner coordination, physical patching) and typically takes weeks to months. Since this customer’s timeline is driven by expiring data-centre contracts, order the circuit early, and consider a hosted connection from an AWS Partner — provisioned in far less time and available in sub-1 Gbps increments — to bridge the gap.

12.3.2 Direct Connect topology

  • SiteLink lets you send data between Direct Connect locations, creating private links across your global offices/data centres.
  • A Direct Connect Gateway is what lets one connection reach multiple VPCs across accounts and Regions — without it, a private virtual interface maps to a single VPC.
  • Each dedicated connection is a single link — so AWS recommends a second connection for redundancy. Without a backup (second DX or an IPsec VPN), VPC traffic is dropped on failure.

12.3.3 The alternatives — and when they’d win

Site-to-Site VPN (virtual private gateway + customer gateway, with redundancy)

Option How it works Prefer when
Direct Connect (chosen) Private, dedicated fibre to AWS; off the public internet You need consistent throughput/latency for high volume
Site-to-Site VPN IPsec tunnel over the internet via a virtual private gateway You want it fast and cheap, or as failover for Direct Connect
Client VPN Managed remote-access VPN (OpenVPN-based) for individual users Remote workforce needs to reach VPC/on-prem resources

⚠️ VPN failover is survival, not capacity. Each Site-to-Site VPN tunnel is capped at roughly 1.25 Gbps. Failing a 10 Gbps Direct Connect over to a VPN is a capacity cliff, not a transparent switch — expect degraded service. For genuinely high-bandwidth production, AWS’s resiliency models recommend two Direct Connect connections at two separate locations (with the VPN as a third line of defence). Also note that when both paths are up, BGP path selection prefers Direct Connect, so failover behaviour depends on correct BGP configuration, not luck.

12.3.4 Scaling connectivity: AWS Transit Gateway

Direct Connect answers one DC to one VPC. Once you have many VPCs, accounts or Regions, point-to-point peering explodes into an unmanageable mesh. Transit Gateway is the hub-and-spoke fix.

  • Each connection is made once to the hub; route tables control who talks to whom.
  • Inter-Region peering links transit gateways over the AWS backbone; that traffic is automatically encrypted and never traverses the public internet — unlike the Direct Connect link itself.
  • Pairs naturally with a Direct Connect Gateway for multi-Region + multi-VPC estates.

For VPC, subnet and routing fundamentals, see 04. Networking.

Architect’s takeaway: Choose Direct Connect for consistent, high-volume hybrid traffic — but order it early, encrypt it explicitly, and size the fallback honestly. Keep a VPN as automatic failover so a single link is never a SPOF, and reach for Transit Gateway + Direct Connect Gateway the moment the topology grows past a couple of VPCs.

12.4 Step 3 — Run the containers, privately

  • ❓ ECS or EKS? EC2 or Fargate? And how do private containers still reach the internet outbound?

12.4.1 Launch-type decision: why EC2, not Fargate

Chosen: Amazon ECS with the EC2 launch type. The customer requires a custom AMI and SSH access to the underlying instances (to keep management operations similar across on-prem and cloud). Fargate supports neither, so EC2 is the correct launch type here — a rare case where the serverless option is rejected on purpose.

ECS on EC2 architecture

  • The ECS agent runs on each EC2 instance and lets ECS orchestrate the nodes you own and manage.
  • Contrast with Fargate, where each task gets its own elastic network interface and there are no EC2 instances to manage — great when you don’t need a custom AMI or host access.
EC2 launch type (chosen) Fargate launch type
You manage The EC2 cluster (AMI, patching, SSH) Nothing below the task
Custom AMI ✅ Yes ❌ No
SSH to host ✅ Yes ❌ No
Best when Custom AMI, host control, consistent tooling “Just run my container”, no infra ops

See 03. Compute for the wider EC2 and container landscape.

12.4.2 Private subnets, outbound egress, and the NAT trap

The containers must be private (no inbound internet) but need outbound (updates). A NAT gateway provides exactly that.

  • A NAT device replaces the private instance’s source IP with its own and translates responses back — so instances initiate outbound connections but can’t receive unsolicited inbound ones.
  • NAT gateway (managed) is recommended over a self-run NAT instance for better availability, bandwidth and less admin.
  • Public NAT gateway (Elastic IP, routes to internet gateway) vs private NAT gateway (routes to other VPCs/on-prem via TGW or VGW, no Elastic IP).

🔴 One NAT gateway is a single point of failure. A NAT gateway is scoped to a single Availability Zone. If you put one NAT gateway in one public subnet and route every private subnet to it, an AZ failure takes all your containers’ egress down — which directly contradicts the customer’s “no single points of failure” requirement. Deploy one NAT gateway per AZ and give each AZ’s private subnet its own route table pointing at its local NAT gateway. This also avoids paying for cross-AZ data transfer on every outbound byte.

💰 Don’t pay NAT charges for traffic that never needed the internet. NAT gateways bill per hour and per GB processed. ECS pulling images from ECR, the SSM Agent, CloudWatch Logs and S3 access all go through NAT by default. Replace that with VPC endpoints: a gateway endpoint for S3 (no hourly charge) and interface endpoints for ECR API/DKR, SSM, and CloudWatch Logs. You cut cost and keep the traffic off the internet path entirely — a better fit for “private containers” than NAT alone.

Architect’s takeaway: “Serverless by default” is not a law. When the driver is a custom AMI + host SSH + consistent tooling, ECS on EC2 is the right call. Pair private subnets with one managed NAT gateway per AZ for resilient outbound-only access, and use VPC endpoints for AWS-service traffic.

12.5 Step 4 — Migrate the database, resiliently

  • ❓ How do you lift-and-shift PostgreSQL with near-zero downtime and no single point of failure?

Chosen: Amazon RDS for PostgreSQL, Multi-AZ, migrated with AWS DMS. A managed engine keeps the app code unchanged (lift-and-shift), Multi-AZ delivers the high availability the customer demands, and DMS moves the data while the source stays live.

For RDS fundamentals, backups and where databases sit in your VPC, see 06. Databases.

12.5.1 High availability: Multi-AZ DB instance (one standby)

  • RDS keeps a synchronous standby in another AZ and fails over automatically — the database endpoint doesn’t change, so applications reconnect transparently.
  • The standby is not readable; it exists purely for availability.
  • A single RDS instance does not self-heal; HA requires Multi-AZ.

12.5.2 Even higher availability: Multi-AZ DB cluster (two readable standbys)

  • This is a different deployment type from the Multi-AZ DB instance above — in the console and docs it is the Multi-AZ DB cluster, available for PostgreSQL and MySQL.
  • Three AZs, two readable standbys: failover typically under ~35 seconds, up to ~2× faster commit latency, plus extra read capacity.

12.5.3 Scaling reads: read replicas

  • Read replicas offload read-heavy / CPU-intensive work (e.g. BI reports) off the primary via asynchronous replication, raising aggregate read throughput.
  • Replicas can be promoted to standalone instances if needed.

Don’t confuse the three: Multi-AZ standby = availability (synchronous, auto-failover, not readable). Multi-AZ DB cluster = availability + some read capacity. Read replica = performance/scale (asynchronous, read-only, replica lag). They solve different problems and are often used together.

12.5.4 Choosing a scaling axis

  • Storage types: General Purpose SSD (broad, bursty), Provisioned IOPS (I/O-intensive DBs, consistent low latency), Magnetic (legacy — avoid for new work).
  • RDS Storage Auto Scaling grows storage automatically toward a max limit with virtually zero downtime.

12.5.5 The migration itself: AWS DMS

  • DMS is a replication server in the cloud: define source + target endpoints, run a task, and it copies data while the source stays fully operational — near-zero downtime (there is still a short cutover window).
  • This is a homogeneous migration (PostgreSQL → RDS PostgreSQL), so no AWS SCT schema conversion is needed. Heterogeneous migrations (e.g. Oracle → PostgreSQL) do need SCT.

⚠️ DMS migrates data, not your whole schema. By default DMS creates only the objects needed to move rows — tables with primary keys. It does not bring across secondary indexes, sequences, default values, foreign keys, constraints, views, triggers or stored procedures. For a homogeneous PostgreSQL move the standard pattern is pg_dump/pg_restore for the schema, then DMS for the bulk data and ongoing change capture. Also, CDC from PostgreSQL requires logical replication on the source (wal_level = logical, or rds.logical_replication on an RDS source) — configure it before you cut over, since it needs a restart.

Architect’s takeaway: For a no-rewrite lift-and-shift, RDS + DMS is the default: managed engine keeps the app unchanged, Multi-AZ gives HA (endpoint-stable failover), read replicas absorb reporting load, and DMS moves data with the source still live — provided you move the schema separately and enable logical replication up front.

12.6 Step 5 — Share storage across the boundary

  • ❓ On-prem apps must keep writing over NFS, yet the data has to live in AWS with low local latency. Which storage service?

Chosen: AWS Storage Gateway (S3 File Gateway) + Amazon S3. The customer must keep the NFS protocol for unmodified on-prem apps and store the files in AWS. File Gateway gives local NFS/SMB access with a local cache (low-latency writes) and asynchronously transfers data to S3.

S3 File Gateway architecture

Why it fits every requirement at once:

  • No refactoring: apps keep talking NFS v3/v4.1 (or SMB).
  • Low latency: transparent local caching buffers apps from network congestion.
  • Cost management: data lands in S3, so lifecycle policies move cold files to cheaper tiers.
  • Future-proof: once fully migrated, apps can read natively from S3 with no extra data move.

⚠️ Two operational caveats. (1) Upload is asynchronous, so there is a non-zero RPO — a file written locally is not instantly durable in S3; size the local cache disk for your write burst and monitor upload lag. (2) If anything writes to the bucket outside the gateway, the gateway won’t see it until you run RefreshCache — so treat a File Gateway bucket as gateway-owned, or automate the refresh.

The wider storage menu (know when each wins):

Service Type Prefer when
S3 Object Data lakes, unlimited scale, lifecycle/tiering
S3 File Gateway Hybrid file → S3 On-prem NFS/SMB with cloud-backed storage
EFS Managed NFS Multi-instance shared file system inside AWS
FSx Managed file (Windows/Lustre/…) Specific file-system software needs
EBS Block A disk attached to one EC2 instance

A note on EBS sizing: with the older gp2, IOPS scaled with volume size, so you over-provisioned capacity to buy performance. gp3 decouples them — a baseline 3,000 IOPS regardless of size, with IOPS and throughput provisioned independently. Prefer gp3 for new volumes.

More on storage classes, durability and lifecycle: 05. Storage.

Architect’s takeaway: When the requirement is “keep NFS but store in AWS,” S3 File Gateway is the purpose-built answer — local cache for latency, S3 for durability and lifecycle, and a clean path to native S3 later. Just be explicit that the upload is asynchronous.

12.7 Step 6 — Operate one way across both environments

  • ❓ The customer wants the same tooling on-prem and in AWS. What makes that possible — and where does it stop?

  • ECS Anywhere runs and manages containers on customer-managed infrastructure using the same ECS APIs, scheduling and monitoring — it needs the ECS + SSM agents installed on local servers, plus outbound connectivity to AWS.
  • AWS Systems Manager gives one control plane: Run Command (scripts across fleets without SSH), Patch Manager, Maintenance Windows, and Parameter Store (config/secrets, KMS-encrypted SecureStrings). Requires the SSM Agent on managed nodes.
  • AWS Backup centralises and automates policy-based data protection across EC2, EBS, RDS/Aurora, DynamoDB, EFS/FSx, Storage Gateway volumes, and on-prem VMware — one place for compliance.

⚠️ “Same tooling” has limits — say them out loud. ECS Anywhere external instances register with the EXTERNAL launch type and do not support awsvpc task networking, Elastic Load Balancing target-group registration, or Fargate. So on-prem tasks are managed by the same control plane but are not operationally identical to cloud tasks — you still need a local load-balancing story. Also, the on-prem side depends on outbound connectivity to AWS: if the link drops, running containers keep running, but you lose orchestration.

Architect’s takeaway: Hybrid operational consistency comes from three pillars — ECS Anywhere (same container tooling), Systems Manager (same ops/automation), AWS Backup (same protection policy) — all reaching into the data centre via agents. Consistent control plane, not identical capability.

12.8 Step 7 — Observe both sides through one pane

  • ❓ Half the estate has no AWS API in front of it. How do you monitor it the same way?

In a hybrid estate the link itself is the component most likely to hurt you and least likely to be watched. Instrument it first.

Signals worth alarming on

Layer Metric Why it matters
Direct Connect ConnectionState, virtual-interface BGP state The earliest, cleanest “the link is gone” signal
Direct Connect ConnectionBpsEgress/Ingress, ConnectionErrorCount Saturation and physical errors before users notice
Site-to-Site VPN TunnelState Confirms the failover path is actually up before you need it
ECS Container Insights, CPUReservation, MemoryReservation, running vs desired task count Desired ≠ running means the cluster can’t place tasks
RDS ReplicaLag, FreeStorageSpace, DatabaseConnections, failover events Replica lag silently makes reports wrong
S3 File Gateway CachePercentDirty, CloudBytesUploaded, FilesFailingUpload Rising dirty cache = the async upload is falling behind (your RPO growing)
DMS CDCLatencySource, CDCLatencyTarget Tells you whether cutover is safe yet

Practices

  • Install the CloudWatch agent on-prem via Systems Manager hybrid activations so data-centre servers publish the same metrics and logs as EC2 — this is what makes “one pane of glass” real rather than aspirational.
  • Alarm on TunnelState of the standby VPN, not just the primary link. An untested failover path is not a failover path.
  • Treat desired-vs-running task count as your container liveness check on both sides.

See 07. Monitoring for CloudWatch fundamentals.

Architect’s takeaway: In hybrid, monitor the seam. BGP state, tunnel state and gateway upload lag are the metrics that tell you the two halves are still one system.

12.9 Step 8 — Scale the moving parts

  • ❓ With ECS on EC2, what exactly scales, and how?

  • Cluster auto scaling grows/shrinks the EC2 fleet via an Auto Scaling group capacity provider with managed scaling.
  • Service auto scaling grows/shrinks the number of tasks using Application Auto Scaling, driven by CloudWatch alarms.
    • Target tracking (recommended) — like a thermostat: pick a metric target, AWS maintains it.
    • Step scaling — adjustments sized to the alarm breach.
  • Don’t forget the DB: RDS Storage Auto Scaling for storage growth.

Architect’s takeaway: With the EC2 launch type you own two scaling dimensions — cluster (hosts) and service (tasks). Prefer target-tracking policies. This is operational work you would not pay with Fargate, and it belongs in the EC2-vs-Fargate trade-off.

12.10 Step 9 — Design for disaster recovery

  • ❓ How much resilience does an enterprise workload need — and what does each level cost?

DR strategies sit on a spectrum from cheap/slow to expensive/instant. The choice is an RTO/RPO vs cost/complexity trade-off.

Strategy What’s running in the recovery Region RTO/RPO Cost & complexity
Backup & restore Nothing; redeploy from backups + IaC Hours Lowest
Pilot light Core (DB replication, storage) on; app servers off Lower Low–medium
Warm standby Scaled-down but fully functional copy always on Minutes Medium
Multi-site active/active Full capacity serving traffic in all Regions Near zero Highest
  • Active/passive (backup/restore, pilot light, warm standby) recovers into a passive site; active/active serves from all Regions.
  • IaC (CloudFormation / CDK) is essential for fast, error-free redeploy — also back up code, config and AMIs, and automate redeploy with CodePipeline.

Active-active vs active-passive topologies are covered further in 08. Optimization.

Make the network itself resilient — back Direct Connect with a Site-to-Site VPN:

Architect’s takeaway: Pick the cheapest DR strategy that still meets your RTO/RPO — most enterprises land on warm standby unless near-zero downtime justifies active/active. And never leave the link as a SPOF: back Direct Connect with a VPN, while remembering the bandwidth cliff from 12.3.3.

12.12 When not to use these choices

Symptom Reconsider Better fit
No custom AMI / no host access needed EC2 launch type Fargate (drop the cluster ops)
Low-volume or temporary connectivity Direct Connect Site-to-Site VPN (cheaper, quick, no lead time)
Migration deadline shorter than DX provisioning Dedicated connection Hosted connection via a partner, or VPN first
Only 1 VPC, 1 account Transit Gateway Direct connection / simple peering
Shared file system inside AWS only S3 File Gateway Amazon EFS
Heterogeneous DB engines One-step DMS DMS + AWS SCT (schema conversion)
On-prem tasks need ELB / awsvpc networking ECS Anywhere Local orchestration, or move the workload to AWS
Near-zero RTO mandated + budget Warm standby Multi-site active/active
Read scaling needed, not availability Multi-AZ standby Read replicas (and vice-versa)

Architect’s takeaway: Every choice here flips with a change in volume, tooling needs, engine compatibility, provisioning time, or RTO budget. “Best fit” = technical + operational + cost, across both environments.

12.13 Architect’s cheat sheet

  1. In hybrid design the network is the foundation — decide connectivity first.
  2. Agree non-overlapping CIDR ranges between data centre and VPC before anything else.
  3. Direct Connect for consistent, dedicated, high-volume DC↔︎AWS traffic (off the public internet).
  4. Direct Connect is private, not encrypted — add MACsec or an IPsec VPN over DX if compliance requires it.
  5. Direct Connect takes weeks to months to provision; use a hosted connection or VPN to bridge a deadline.
  6. Always add a VPN failover for Direct Connect — a single link is a SPOF; without backup, VPC traffic drops.
  7. VPN failover is survival, not capacity: ~1.25 Gbps per tunnel. Two DX at two locations is the real HA answer.
  8. Site-to-Site VPN = cheap/quick or failover; Client VPN = remote workforce access.
  9. Transit Gateway turns an unmanageable VPC mesh into a hub; a Direct Connect Gateway reaches many VPCs/Regions.
  10. ECS on EC2 when you need a custom AMI or SSH; Fargate can’t do either.
  11. Private subnets + managed NAT gateway = outbound-only internet; no unsolicited inbound.
  12. A NAT gateway is AZ-scoped — deploy one per AZ, or you have re-created the SPOF you were told to remove.
  13. Use VPC endpoints (S3 gateway; ECR/SSM/Logs interface) to cut NAT data-processing cost and stay off the internet.
  14. RDS + managed engine = lift-and-shift with no app rewrite.
  15. Multi-AZ DB instance = availability (synchronous, non-readable standby, auto-failover, endpoint unchanged).
  16. Multi-AZ DB cluster (PostgreSQL/MySQL) = two readable standbys, ~35 s failover, ~2× faster commits.
  17. Read replica = performance (asynchronous, read-only, replica lag). Don’t confuse it with a standby.
  18. Scale RDS by the right axis: vertical (CPU+storage), replicas (read CPU), Storage Auto Scaling, Provisioned IOPS.
  19. DMS migrates data, not full schema — no secondary indexes, sequences, FKs or procedures. Use pg_dump/pg_restore for schema.
  20. CDC from PostgreSQL needs logical replication enabled on the source before cutover.
  21. S3 File Gateway = keep NFS/SMB locally with a cache, store in S3 async — no app refactor.
  22. File Gateway upload is asynchronous (real RPO), and out-of-band bucket writes need RefreshCache.
  23. Know the storage menu: S3 (object), EFS (cloud NFS), FSx (specific FS), EBS (block); prefer gp3, which decouples IOPS from size.
  24. ECS Anywhere runs ECS-managed containers on your own hardware — but no awsvpc, no ELB target groups, no Fargate.
  25. Systems Manager (Run Command, Patch, Parameter Store) + AWS Backup centralise hybrid ops and protection.
  26. Install the CloudWatch agent on-prem via SSM hybrid activations — that is what makes one pane of glass real.
  27. Monitor the seam: DX ConnectionState/BGP, VPN TunnelState, gateway CachePercentDirty, DMS CDC latency.
  28. ECS on EC2 has two scaling layers: cluster (hosts) and service (tasks) — prefer target tracking.
  29. DR spectrum: backup/restore → pilot light → warm standby → active/active (cost ↑, RTO ↓); use IaC for redeploy.
  30. “Serverless by default” is not a law — ECS on EC2 here proves fit beats fashion.
